# Design：云端上传按 2MB 请求体上限自动压缩

> **Change**：`2026-11-23_cloud_upload_size_limit`

## D1 为什么在客户端解决

云托管入口的请求体上限是**平台能力边界**（网关层），后端拿不到请求、也改不了上限。可选路径：

| 方案 | 成本 | 结论 |
|---|---|---|
| 客户端压缩到安全阈值 | 小（仅前端） | ✅ 本次采用 |
| 分片上传 / 直传 COS | 大（协议 + 后端 + 鉴权 + 清理） | 另立 change |
| 调大云托管上限 | 平台不支持 | ❌ |

## D2 阈值与压缩梯度

```
CLOUD_SAFE_BYTES = 1800 * 1024        // 1.8MB，留 multipart 头 / boundary 余量
CLOUD_COMPRESS_QUALITIES = [85, 70, 55, 45]
```

- 云端模式：按梯度逐档压缩，`size <= 1.8MB` 即停；仍超 → 提示"请裁剪或重新拍摄"，**不发请求**；
- 本地模式：保持原策略（`> 800KB` 才 `quality 85` 压一次），因为本地无网关限制且过度压缩会掉 OCR 识别率。

## D3 模式判定

与 `src/utils/upload.ts` 完全一致：`VITE_USE_LOCAL` 显式优先，否则 `import.meta.env.DEV` 视为本地。
两端规则若不一致会出现"压缩了但传到本地"或反之的诡异行为，故在 `ExamUpload.vue` 内复制同一 `resolveUseLocal`（注释标注同源）。

## D4 不影响 OCR 质量的边界

- **不 resize**：只降 JPEG 质量，长边像素数不变（后端 1193 的分辨率下限仍按原图判定）；
- 1.8MB 对 2000~3000px 的试卷照片通常足以保留小字（质量 70~85 档位）；
- 若某张图压到 quality 45 仍 >1.8MB（极高分辨率/噪点多的照片），提示用户裁剪或重拍，避免"传上去也糊"。
