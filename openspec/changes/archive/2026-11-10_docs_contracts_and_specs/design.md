## 3. 新增 #21：枚举双形态

```markdown
### 约定 #21：枚举的「DB 形态」与「API 形态」必须成对修改

- 约定内容：带持久化的枚举（如 RecordType）存在两种形态——
  DB / MyBatis XML 使用枚举名（HOMEWORK），API JSON 使用 @JsonValue 标注的 code（homework）。
  修改其中一处时必须同步另一处。
- 影响范围：RecordType、PlanStatus、ErrorQuestionSourceType、AgentType 等所有落库枚举
- 违反后果：只改一边会导致 MyBatis 无法映射（enum 解析失败）或前端拿到英文枚举名
- 发现时间：2026-11-09（recordType 显示英文）
```

选它作为 #21 的理由：这是唯一一条**两个月内被踩两次**的约定（先 `PlanStatus`、后 `RecordType`），且症状不直观（一个是 SQL 报错，一个是界面显示英文），最值得固化。

## 4. Spec 文件划分

`openspec/specs/` 只写「运行时行为 + 契约」，不复制 `docs/architecture/index.md` 的分层与包结构。

| 文件 | 回答的问题 | 不写什么 |
|------|-----------|---------|
| `system-overview.md` | 系统由哪几块组成、请求怎么流、有哪些状态机、外部依赖是什么 | 代码目录树、Maven 依赖清单 |
| `learning-loop.md` | 「设目标 → 计划 → 作业 → 评测 → 试卷 → 调整」每一步落在哪个接口/表/规则 | 产品规则的动机与公式推导 |
| `agent-contracts.md` | 每类 Agent 的输入输出、降级动作、日志与脱敏、当前落地状态 | Prompt 正文 |
| `mastery-and-records.md` | 掌握度怎么变、追溯链怎么连、学习记录为何只读 | 公式的设计意图（属 product/index.md 规则 #2） |

**写作规则**：

1. 每条断言必须能指出代码落点（类名 + 方法名），无法指出的一律不写
2. 与 `docs/product/index.md` 冲突时以 product 为准，并回头修正 spec
3. 明确标注"未落地"的部分（如 OCR、规划 Agent），避免 spec 变成愿景
4. 每份 spec 顶部写明维护触发条件：**change 归档时，若改变了该 spec 描述的行为，必须同轮更新**

## 5. 维护规则（写入 spec 顶部）

```
> 维护触发：change 归档时，若本次变更改变了本文件描述的行为，必须在同一轮更新本文件。
```
