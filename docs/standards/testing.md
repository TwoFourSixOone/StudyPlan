# 测试规范

> 本文件定义项目的测试要求和标准，确保测试质量可控。
>
> **注释约定**：本文件中 `<!-- ... -->` 形式的注释用于解释规则背后的原因，帮助开发者理解“为什么”而非仅知道“做什么”。

---

## 1. 测试原则

<!--
  为什么这三条？
  - “每个 change 必须有测试”防止功能新增后无回归保障。
  - “覆盖正常+异常”防止只测快乐路径、上线后异常分支全部裸奔。
  - “未覆盖必须说明”让评审者能判断剩余风险是否可接受，而不是默认忽略。
-->

- 每个 change 必须包含对应的测试用例
- 测试必须覆盖正常路径和关键异常路径
- 未覆盖的测试场景必须显式说明原因

---

## 2. 测试分层

### 单元测试

<!--
  为什么选 JUnit 5 + Mockito？
  - JUnit 5 是 Java 17 生态的标准测试框架，支持参数化测试、嵌套测试、动态测试等现代特性。
  - Mockito 用于隔离 Service 层的外部依赖（DAO、Agent 调用等），使单元测试不依赖数据库或网络。
  - 两者均为 Spring Boot 官方 starter-test 的默认组件，无需额外引入。
-->

- **范围**：Service 层核心业务逻辑
- **框架**：JUnit 5 + Mockito
- **要求**：
  - 覆盖正常路径（happy path）
  - 覆盖关键异常路径（参数为空、数据不存在、权限不足等）
  - 覆盖边界场景（空集合、最大值、最小值等）
  - 每个测试方法必须有明确的断言

### 集成测试

<!--
  为什么集成测试要单独覆盖 Controller 层？
  - Controller 是 HTTP 入口，涉及参数校验、状态码返回、异常处理等，单元测试无法完全模拟。
  - 跨模块调用（如 Service → DAO → DB）需要验证事务边界是否正确，避免脏数据。
  - 集成测试使用 @SpringBootTest 启动真实容器，能发现单元测试覆盖不到的配置问题。
-->

- **范围**：Controller 层接口、跨模块调用
- **要求**：
  - 验证接口入参和出参
  - 验证异常状态码返回
  - 验证事务边界

## 3. 测试命名规范

<!--
  为什么采用 should_[预期行为]_when_[条件] 格式？
  - 测试名即文档：读方法名就能知道测的是什么场景、期望什么结果，降低理解成本。
  - 失败时快速定位：CI 报红时，方法名直接指出是哪个场景出了问题，无需打开代码。
  - 团队一致性：统一命名风格避免各写各的，评审时减少无谓的格式争论。
-->

```
测试方法名：should_[预期行为]_when_[条件]
示例：should_returnUser_when_idExists        // 正常路径：ID 存在时返回用户
      should_throwException_when_idIsNull     // 异常路径：ID 为空时抛异常
      should_returnEmptyList_when_noData      // 边界场景：无数据时返回空集合
```

## 4. 测试覆盖要求

<!--
  覆盖率阈值是怎么定的？
  - Service 层 80%：核心业务逻辑（掌握度公式、作业裁剪、降级策略等）必须充分覆盖，
    剩余 20% 通常是极少数难以触达的防御性分支。
  - Controller 层 60%：Controller 本身逻辑较薄（参数校验 + 转发），重点覆盖入参校验和状态码，
    不需要像 Service 那样严格。
  - DAO 层“视情况”：简单 CRUD 无需单独测试（由集成测试覆盖），但复杂 SQL（如批量更新、
    多表关联查询）必须有对应测试用例。
-->

| 层级 | 最低覆盖率 | 说明 |
|------|-----------|------|
| Service 层 | 80% | 核心业务逻辑必须充分覆盖 |
| Controller 层 | 60% | 接口入参出参验证 |
| DAO 层 | 视情况 | 复杂 SQL 需要测试 |

---

## 5. 评审摘要中的测试说明

每次 `/prepare-review` 生成的评审摘要中，必须包含：

- 本次变更跑了哪些测试
- 哪些场景没有测
- 为什么当前可以接受这些未覆盖的场景

---

## 6. 禁止事项

<!--
  为什么禁止这三项？
  - “禁止只有 happy path”：大量项目实测后发现，异常路径的 bug 密度远高于正常路径，
    只测正常路径等于放弃了测试最有价值的部分。
  - “禁止没有断言”：没有断言的测试永远通过，是“假安全感”，比不写测试更危险。
  - “禁止互相依赖执行顺序”：顺序依赖导致测试脆弱，单独运行某个用例会失败，
    CI 并行执行时也会出问题。
-->

- 禁止只有 happy path 的测试
- 禁止没有断言的测试
- 禁止测试之间互相依赖执行顺序

## 7. 产品规则场景测试要求

> 对应 `docs/product/index.md` 中的核心规则，以下场景必须有对应测试用例。

<!--
  为什么要把产品规则映射到测试场景？
  - 产品规则是业务行为的“契约”，测试是契约的“执行保障”。
  - 每条规则至少有一个测试用例覆盖，才能在重构时确保业务行为不漂移。
  - 当规则变更时（如掌握度公式参数调整），对应测试同步更新，形成闭环。
-->

| 产品规则 | 必须覆盖的测试场景 |
|---------|------------------|
| 规则 #2（掌握度公式） | 答对/答错时掌握度变动方向正确；来源权重差异体现；变更日志记录完整；D_norm 校验：原题用题库元数据难度、新题偏离 > 0.2 时降级为 0.5 |
| 规则 #3（作业粒度） | 单日 ≤15 题硬上限；单知识点 ≤4 题（1 原题 + 最多 3 道举一反三）；原题优先占位、新题按剩余配额分配；错题堆积 ≥15 时兜底逻辑（举一反三全部暂停）；错题重做为原题、举一反三为新题；无错题时每知识点 2~3 道常规新题；新题相似度 > 0.8 触发重试 |
| 规则 #4（试卷解析） | 切题重试与归因重试独立计数；未识别题目标记为待人工归因 |
| 规则 #5（计划调整） | “无需调整”与“降级”两种状态分别返回、前端可区分；触发信号命中/未命中行为差异 |
| 规则 #6（Agent 降级） | 四类 Agent 各自的降级行为；降级事件记录日志 |
| 规则 #7（tenant_id + JWT） | 所有查询携带 tenant_id；新增记录 tenant_id 不为 NULL；JWT 过期后静默刷新 |
| 规则 #9（学习记录） | 学习记录只追加不删除；系统日志只追加不删除；追溯链完整 |
| 规则 #10（数据导入） | JSON 导入时逐条校验；校验失败记录错误日志且不阻塞其他记录；知识点导入后待校对、题目立即生效；ID 冲突时跳过并警告；导入完成后返回统计摘要；导入操作记录完整 |
