## 0. 术语表

| 术语 | 定义 | 说明 |
|------|------|------|
| 知识点掌握度（mastery） | 学生在某知识点上的结构化评分（0.0–1.0） | 统一使用"掌握度"作为简称 |
| 置信度（confidence） | 系统对掌握度评分的可信程度（0.0–1.0），随评测次数与来源权重递增 | — |
| 每日作业 | 由出题 Agent 按当日计划生成的练习题集合，含知识回顾、针对性练习（错题重做 + 举一反三）、综合提升三类 | 统一使用"每日作业"，不简写为"作业"以避免歧义 |
| 专项评测 | 针对单个或多个知识点的集中评测任务，权重高于每日作业 | — |
| 计划调整 | 由调整 Agent 基于触发信号输出的计划 diff（仅修改有问题的日期） | 统一使用"计划调整"，不简写为"调整" |
| 计划 diff | 调整 Agent 的结构化输出，包含需修改的日期列表及对应的新任务内容 | — |
| 触发信号 | 后端预定义的条件表达式，用于判断是否需要生成计划 diff | 详见规则 #5 |
| 知识点归因 | 将一道题目映射到一个或多个知识点的过程 | — |
| 学习记录 | 学生在系统中产生的全部学习行为数据的统称，包含每日作业提交记录、专项评测结果、考试试卷分析结果 | 详见规则 #9 |
| 题库 | 系统中所有题目的集合，每道题关联一个知识点，含题干、选项、答案、解析、难度、题型 | 详见规则 #10 |
| 知识点树 | 按"章节 → 知识点 → 子知识点"三级组织的知识体系，每个知识点有唯一 ID、状态标记、先修关系 | 详见规则 #8/#10 |
| 课程标准条目 | 教育部发布的各学段各学科内容要求，知识点通过 `standards` 字段关联到对应条目 | 详见规则 #10 |

## 1. 产品概述

智学伴（StudyMate）是一款面向初中、高中学生的 **AI 自适应学习辅助小程序**（uni-app 开发，编译目标为微信小程序，Demo 阶段仅此一端）。本项目的核心定位是：**跑通"设定目标 → Agent 规划每日计划 → 完成每日作业 → 知识点评测 → 考试试卷分析 → Agent 动态调整计划"的完整学习闭环**，以知识点掌握度为状态、以 LLM Agent 为决策引擎，实现个性化、可追溯的学习计划管理。

### 1.1 功能模块概括

系统分为学生端（uni-app 小程序）、管理后端（PC 端 Vue 3）、后端服务、AI Agent 服务四部分，功能模块如下：

**（1）学生端（uni-app 小程序）**

- **学习目标设定**：选择科目、指定大学习方向与目标（如"本学期数学冲 110 分"）、设定目标周期
- **计划总览**：查看 Agent 生成的阶段计划与每日计划，按日期浏览作业安排
- **每日作业**：查看当日作业（知识回顾、错题重做、举一反三、综合提升），逐题作答并提交
- **知识点评测**：对当前知识点掌握情况进行专项评测，生成评测结果
- **试卷上传**：按科目上传学校考试试卷图片，触发 AI 分析与知识点归因
- **掌握度看板**：按科目查看各知识点掌握度、置信度与变化趋势
- **计划调整**：点击按钮触发 Agent 根据计划完成情况、作业结果、考试分数、知识点掌握度进行计划调整，调整结果需用户确认后生效
- **订单式状态查看**：查看每日作业完成状态、评测记录、调整历史

**（2）后端服务（Spring Boot）**

- 统一响应结构（Result）、全局异常处理
- 学生登录态（openid 静默登录 + JWT 鉴权）与权限控制
- 科目管理、**知识点树管理（导入、校对、分级、启停用）**、学习目标管理
- 每日计划与作业的存储、下发、提交批改
- 知识点掌握度状态表的维护与更新（可解释、可回滚）
- 试卷上传、异步解析任务管理
- 计划调整触发、diff 结果存储与确认
- MySQL 5.7+ 数据存储，表结构预留 `tenant_id`（暂不实现多租户）
- **MySQL 5.7 限制说明**：不支持 `jsonb`（仅 `json` 类型，不支持函数索引）、不支持 `CHECK` 约束（8.0 才支持）、不支持部分索引。因此：数值范围校验在**应用层实现**，不依赖 DB 约束；JSON 字段使用 `json` 类型且不建函数索引；所有表字符集统一使用 `utf8mb4`（支持数学符号与 emoji）。

**（3）AI Agent 服务（AgentScope Java 嵌入 Spring Boot）**

- **规划 Agent**：将大目标拆解为阶段计划与每日计划
- **出题 Agent**：按知识点与掌握度生成每日作业题目
- **归因 Agent**：对每日作业作答与试卷题目做题目级知识点判定
- **调整 Agent**：基于结构化状态数据输出计划 diff（仅修改有问题日期）
- 所有 Agent 输出强制结构化 JSON，经校验后落库；**Agent 只能引用知识点表中的知识点 ID，不得自由生成知识点**

**（4）管理后端（PC 端，Vue 3 + Element Plus + Vite）**

> 以下模块仅供开发者使用，PC 端浏览器访问，不在学生端小程序中体现。**管理后端属于 Demo 交付范围**（开发者需在 Demo 中展示数据准备与导入流程），但学生端不可见。

- **题库管理**：题目列表与 JSON 文件批量导入
- **知识点管理**：知识点列表与 JSON 文件批量导入
- **先修关系管理**：先修关系列表与 JSON 文件批量导入
- **课程标准管理**：课程标准列表与 JSON 文件导入
- **导入日志查看**：查看数据导入操作记录与错误记录

> 列表页搜索框、分页、组件选型等 UI 实现规范参见 `docs/architecture/index.md` §2「管理后端前端架构」。

**（5）平台侧（仅开发者可见，不属于 Demo 演示范围）**

> 以下模块仅供开发调试使用，不属于 Demo 评审范围。

- Knife4j/Swagger 接口文档
- LLM Gateway（多 Provider 路由与降级）
- Prompt 版本管理
- 异步任务队列（试卷解析、批量出题、计划调整）

## 2. 核心业务规则

### 规则 #1：学习目标与科目绑定

- **规则描述**：学生设定学习目标时必须指定科目、学习方向与目标周期；一个目标只属于一个科目，计划与每日作业均按科目分类管理。
- **适用场景**：目标设定、计划生成、每日作业下发、试卷上传、掌握度查看。
- **边界条件**：
    - 未设定目标时不可生成计划。
    - 科目未初始化知识点树时不可生成每日作业。**"初始化完成"的判定标准为：该科目下存在 ≥1 个状态为已启用（`active`）的知识点**。
    - 目标周期结束后，该目标下的计划不再生成新每日作业，历史数据保留只读。

### 规则 #2：知识点掌握度以结构化状态表为准

- **规则描述**：知识点掌握度由后端根据题目级判定结果按公式更新，**不由 LLM 直接给出掌握度数值**。掌握度取值范围 0.0–1.0，每次变更均记录追溯日志。
- **适用场景**：每日作业提交、知识点评测、试卷分析、计划调整。
- **更新公式**：

**答对时（掌握度上升）：**

```
delta_m_up = alpha * W_source * D_norm * C_norm * (1 - m_current)
m_new = min(1.0, m_current + delta_m_up)
```

**答错时（掌握度下降）：**

```
delta_m_down = alpha * W_source * D_norm * C_norm * m_current
m_new = max(0.05, m_current - delta_m_down)
```

> **设计意图说明**：答对时变动量与 `(1 - m_current)` 成正比——掌握度越高提升空间越小，符合学习曲线边际递减规律。答错时变动量与 `m_current` 成正比——掌握度越高却答错，说明存在严重理解偏差，应给予更大幅度的修正惩罚；掌握度低时答错则惩罚较轻（本身尚在入门阶段）。

其中：
- `m_current`：当前掌握度（0.0–1.0）
- `alpha`：基础学习率，默认 0.3（可通过系统配置调整，**允许配置范围 0.1–0.5，超出范围拒绝保存**）
- `W_source`：来源权重，考试 = 1.0，专项评测 = 0.7，每日作业 = 0.4
- `D_norm`：难度归一化值（0.3–1.0），难度越高对掌握度变动影响越大。**取值来源**：原题（错题重做）使用题库元数据中的难度值（已知且可信）；Agent 生成的新题（举一反三）使用生成时声明的难度值，但需与同知识点历史题目难度均值做合理性校验——若偏离 > 0.2，则降级为默认值 0.5，防止 Agent 虚标难度。
- `C_norm`：置信度衰减因子，计算公式 `C_norm = 1.0 - 0.5 * confidence`，取值范围（0.5–1.0）。**置信度越低时 `C_norm` 越大**，鼓励在评测初期快速收敛。
- 答错时保留最低值 0.05，避免完全归零。

- **置信度更新**：每次有效评测后置信度递增（含答对与答错），初始值为 0.1。
- **追溯记录**：每次掌握度变更记录变更类型（作业/评测/考试）、来源、变动量、变更前后的值。
- **边界条件**：掌握度看板仅展示已启用（`active`）的知识点，已停用（`disabled`）的知识点在历史记录中保留但标记为"已停用"且不可选。

> **观察项（非缺陷）**：当 `m_current` 很低时，答错公式的变动量极小，配合最低值 0.05，可能出现"低掌握度反复答错但掌握度几乎不动"的平台期。当前设计选择是"低掌握度惩罚轻"（入门阶段鼓励继续尝试）。若后续数据发现影响体验，可考虑对低分段改用固定惩罚项。

### 规则 #3：每日作业的组成与粒度

- **规则描述**：每日作业由出题 Agent 生成，包含三类任务：知识回顾、针对性练习（含"错题重做"与"举一反三"）、综合提升。每知识点的针对性练习结构为：**1 道原题重做 + 2~3 道 Agent 模拟新题（举一反三）**。
- **适用场景**：每日计划生成、学生端作业展示。
- **错题重做（原题）细则**：
    - **原题定义**：学生之前在每日作业、专项评测或考试中答错的题目，其题目内容**完全不变**地从历史题库中抽取。
    - 抽取周期：按 1/3/7/15/30 天艾宾浩斯周期抽取到期错题。
    - 起算时间：从学生**首次答错该题之日**起算。
    - 同一错题多次答错：每次答错后重置艾宾浩斯周期。
    - 周期内若该知识点掌握度已 ≥ 0.8，则该错题**暂停重做**，保留记录。
    - **重新入队规则**：若该知识点掌握度后续跌破 0.8，之前暂停的错题**自动重新入队**，从下一个未到达的周期节点开始重做。
    - 超过 30 天周期仍未答对的原题，标记为"需重点关注"，由调整 Agent 在计划调整时优先处理。
- **举一反三（Agent 模拟新题）细则**：
    - **定义**：针对学生答错的知识点，由出题 Agent **生成 2~3 道新题**，考查同一知识点但题目内容不同，难度递进。
    - **生成要求**：
        - 新题必须关联同一知识点。
        - 新题不得与原题重复（题干、选项、解题步骤均需不同）。
        - 第 1 道新题：与原题难度相当，巩固同一解法。
        - 第 2 道新题（若有）：难度略升或变换题型。
        - 第 3 道新题（若有）：综合性更强。**Demo 阶段不强制涉及先修知识点**。
    - **触发条件**：有到期错题时，为对应知识点生成举一反三新题；无错题时，按掌握度从低到高常规出题，**每知识点出 2~3 道常规新题，单知识点上限仍为 4 题**。
    - **新题存储**：Agent 生成的举一反三新题写入 `generated_question` 表，与题库表（`question_bank`）分开存储，学生作答后归因流程与题库原题一致。
    - **存量新题与知识点状态联动**：若 `generated_question` 中某新题关联的知识点后来被停用（`disabled`），该新题不再进入新的每日作业，但已完成作答的记录保留（符合规则 #9 只读不删）。
    - **新题重复校验**：出题 Agent 生成新题后，后端进行**题干相似度检测**（阈值 0.8）。相似度 > 0.8 触发重试（最多 2 次）；重试仍失败则跳过该题、减少 1 道举一反三新题。
- **定量边界**：
    - 单日每日作业总量上限：**≤ 15 题**（含三类任务合计）。
    - 单知识点每日出题上限：**≤ 4 题**（1 道原题 + 最多 3 道举一反三新题）。
    - 单日作业量下限：若剩余活跃知识点数为 0 或目标周期已结束，则不生成每日作业。
- **计数口径与裁剪规则**：
    - 15 题上限为**硬性总上限**。
    - **原题优先、新题配额制**：错题重做（原题）不可压缩，优先占位；举一反三新题按剩余配额分配。具体裁剪流程：
        1. 先统计当日到期原题总数。
        2. 若到期原题数 ≥ 15，触发**极端场景兜底**（见下方）。
        3. 否则，剩余配额分配给举一反三新题与知识回顾。
        4. 有错题的知识点：每个至少分配 1 道举一反三新题（最低保障）。若剩余配额不足以覆盖所有有错题知识点的最低保障，则**按掌握度从低到高依次分配，配额用完即止**，未分配到新题的有错题知识点仅保留原题重做。
        5. 无错题的知识点：按掌握度从低到高，每个分配 2~3 道常规新题，直到配额用完。
        6. 若配额充足，有错题知识点的举一反三新题可扩展至 2~3 道（与原题合计不超过单知识点 4 题上限）。
    - **当知识点数较多导致配额不足时**：优先保障低掌握度知识点，高掌握度知识点的新题可压缩至 0 道。
    - **极端场景兜底**：若当日到期错题数本身 ≥ 15 题，则错题重做独占当日全部题量，**举一反三全部暂停（含最低保障）与知识回顾当日暂停**；错题按到期时间先后取前 15 题，其余**顺延至次日**（不视为未完成，不触发规则 #5 的 SIG-3 信号）。
- **边界条件**：每日作业必须关联到具体知识点；掌握度低的知识点优先出基础题，掌握度高则出综合题。

### 规则 #4：试卷上传按科目分类与异步解析

- **规则描述**：试卷必须按科目上传；上传后进入异步解析流程，先通过**视觉模型（OCR + 版面分析）切题**得到题目列表，再由归因 Agent 逐题做知识点归因，**不直接让 LLM 输出"薄弱点总结"**。
- **适用场景**：学生上传考试试卷、查看分析结果。
- **切题环节的实现归属**：切题由**独立的视觉模型完成，不属于四类 Agent 中的任何一个**，其重试与归因 Agent 的重试独立计数。
- **边界条件**：
    - 切题失败需保留原图并允许重试（最多 2 次）。
    - 试卷归因结果按考试来源权重（`W_source = 1.0`）更新掌握度。
    - 未识别出知识点的题目标记为**待人工归因**，由开发者通过后端管理接口处理。
    - 切题重试 2 次后仍无法识别的题目，保持待人工归因状态，不阻塞试卷其他题目的归因流程。
    - **重试层级说明**：规则 #4 的"重试 2 次"指**试卷切题环节**，规则 #6 的"重试 2 次"指 **Agent 结构化输出校验环节**，两者**独立计数、互不共享配额**。

### 规则 #5：计划调整基于触发信号与 diff 输出

- **规则描述**：计划调整由用户点击按钮触发，但调整 Agent 的输出必须基于后端预定义的触发信号，且**只输出需要修改日期的计划 diff**，不得重新生成整份计划。
- **适用场景**：学生点击"调整计划"按钮。
- **触发信号定义**（满足任一即命中）：
    - SIG-1：某知识点连续 3 次每日作业正确率 < 60%
    - SIG-2：某知识点掌握度单次考试下降 > 0.15
    - SIG-3：连续 2 天每日作业未完成
    - SIG-4：剩余目标天数与未覆盖知识点量不匹配（预计无法在周期内完成）
- **无信号命中时的系统行为**：返回"暂无需调整"提示，**不调用调整 Agent，不生成 diff**。
- **降级时的系统行为**：触发信号命中但调整 Agent 失败且重试耗尽时，返回"请稍后重试"提示，**不生成 diff，不调用确认流程**。两种状态前端需分别展示不同提示。
- **边界条件**：
    - 调整结果需先展示给学生确认，确认后才生效。
    - 已通过且无问题的日期保留不变。
    - 调整历史需可追溯，记录触发信号列表、diff 内容、用户确认时间。

### 规则 #6：Agent 输出必须结构化且可校验

- **规则描述**：规划、出题、归因、调整四类 Agent 的输出均强制为约定 JSON Schema 的结构化结果，由后端校验后落库；校验失败自动重试（最多 2 次），重试失败则按降级策略处理。
- **适用场景**：所有 Agent 调用。
- **降级策略**（按 Agent 类型分别定义）：

  | Agent 类型 | 降级行为 | 用户提示 |
    |-----------|---------|---------|
  | 规划 Agent | 返回基于模板的默认计划（按目标周期均匀分配知识点） | "已生成默认学习计划，您可稍后手动调整" |
  | 出题 Agent | 返回空每日作业，标记为"待生成" | "今日每日作业生成失败，请稍后重试" |
  | 归因 Agent | 将相关题目标记为待人工归因，不更新掌握度 | "部分题目归因失败，开发者将后续补充" |
  | 调整 Agent | 返回空 diff，响应"调整暂时失败" | "计划调整暂时失败，请稍后重试" |

- **边界条件**：
    - Prompt 版本化管理，不硬编码。
    - Agent 不得直接写业务表，必须经后端 Service 解析入库。
    - 所有降级事件需记录日志，供开发者排查。

### 规则 #7：学生登录态与数据隔离

- **规则描述**：学生端静默获取 `openid` 作为登录态，不强制手机号授权；所有学习数据按学生隔离；接口鉴权采用 JWT (JSON Web Token)。
- **适用场景**：小程序端所有接口。
- **登录与鉴权流程**：
    - 学生端通过微信小程序静默登录获取身份标识，后端签发 JWT。
    - **JWT 有效期**：2 小时，过期后前端静默刷新，无需用户操作。**刷新时序**：前端在 JWT 过期前 5 分钟内发起请求时，后端返回新 JWT（通过响应头携带），前端自动替换本地令牌；若请求到达时 JWT 已过期，后端返回 HTTP 401，前端拦截后自动执行静默刷新并重放原请求（单次重放，不循环）。
- **边界条件**：
    - 身份标识缺失或无效时返回未登录态（HTTP 401）。
    - 表结构预留 `tenant_id` 字段，**Demo 阶段以固定租户 `'default'` 运行**，后续多租户改造时零成本切换。
    - 新增记录时 `tenant_id` 默认填充 `'default'`，不允许为 NULL。

### 规则 #8：知识点来源与治理

- **规则描述**：知识点树是系统的"课程大纲"数据源，Agent 生成计划、出题、归因时**只能引用已启用的知识点**。初期知识点数据来自公开数据集导入，允许标记"待校对"，但必须经过治理流程才能被 Agent 使用。
- **适用场景**：系统初始化、科目扩展、Agent 调用。
- **边界条件**：
    - **数据来源**：初期以 `cn-math-taxonomy` 数据集为主数据源导入；后续扩展科目时需按置信度过滤低置信度条目并人工核对模块完整性。
    - **分级结构**：知识点按"章节 → 知识点 → 子知识点"三级组织。粗粒度知识点由**开发者通过后端导入工具补充子节点**，不得让 Agent 自行拆分。
    - **状态标记**：知识点有三种状态——待校对（`pending_review`）、已启用（`active`）、已停用（`disabled`）。以下情况标记为待校对：
        - 导入时数据集中置信度 < 0.8
        - 导入时无对应子节点拆分
        - 开发者手动标记

      待校对的知识点不参与 Agent 出题与归因。**校对 SLA：导入后 7 个工作日内完成校对**（Demo 阶段为自律目标），超期未校对的知识点触发告警提醒。
    - **先修关系**：保留知识点间的先修边（`hard` / `soft`），供后续使用；Demo 阶段可只存储不使用。
    - **唯一标识**：知识点 ID 一经分配不得复用；数据集更新时以"新增 + 停用"方式处理。
    - **停用知识点展示规则**：已停用的知识点在掌握度看板中**默认隐藏**，但提供"显示历史知识点"开关；开启后以灰色标记展示。历史掌握度记录永久保留。

### 规则 #9：学习记录与回溯查看

- **规则描述**：系统完整记录学生的全部学习行为数据（统称"学习记录"），作为掌握度变更的依据来源与学习效果的回溯凭证。学习记录是"可解释、可追溯"核心定位的数据基础，所有掌握度变动必须能关联到具体的学习记录。
- **适用场景**：掌握度看板展示、计划调整决策、试卷分析回查、开发者排查问题、学生回顾学习历程。
- **学习记录包含以下三类数据**：
    - **每日作业提交记录**：每道题的提交答案、对错判定、关联知识点、提交时间。其中举一反三新题的作答同时关联到 `generated_question` 记录 ID，形成完整追溯。
    - **专项评测结果**：得分、涉及的知识点列表、各知识点正确率、评测时间。
    - **考试试卷分析结果**：逐题归因结果（含知识点映射）、得分、分析时间。
- **回溯查看规则**：
    - 学生端可按日期浏览历史学习记录。
    - 开发者可通过后端管理接口按学生 + 时间范围 + 记录类型查询学习记录。
    - 学习记录**只读不删**——一旦写入不得修改或删除。
    - 学习记录与掌握度变更日志通过关联字段形成完整的"行为 → 状态变化"追溯链。
    - **系统日志的只读不删原则**：掌握度变更日志、计划调整日志、Agent 降级日志、校对提醒记录均**只追加不删除**。
- **边界条件**：
    - 学习记录按学生隔离，学生只能查看自己的记录。
    - Demo 阶段不提供学习记录的导出功能，不提供按知识点的**历史趋势统计图表**（掌握度看板仅展示当前掌握度值、置信度与最近一次变化方向）。

### 规则 #10：题库与知识点数据导入管理

- **规则描述**：系统的基础数据（知识点、题目、先修关系、课程标准）通过 JSON 文件批量导入数据库，由开发者通过后台管理接口触发导入流程。导入后数据进入规则 #8 的治理流程。
- **适用场景**：系统初始化、科目扩展、题库更新、知识点数据修正。
- **导入数据类型**：

  | 数据类型 | 初始 JSON 文件 | 导入后状态 |
  |---------|----------------|----------|
  | 知识点 | `topics.json` | 待校对（`pending_review`），需经规则 #8 校对后才可启用 |
  | 题目 | `questions.json` | 立即生效，可供出题 Agent 使用 |
  | 先修关系 | `dependencies.json` | 立即生效 |
  | 课程标准 | `cn-curriculum-standards.json` | 只读参考数据 |

- **导入流程**：
    1. 开发者通过后台管理接口触发导入任务，指定 JSON 文件路径或上传文件。
    2. 后端解析 JSON 文件，逐条进行**完整性校验**（必填字段、ID 唯一性、外键引用合法性）。注意：完整性校验≠内容校对，校验仅检查数据格式与引用关系，不涉及知识点内容的教学准确性审核。
    3. 校验通过的记录写入数据库，校验失败的记录单独记录失败原因，**不阻塞其他记录导入**。
    4. 导入完成后返回统计摘要（成功数、失败数、跳过数）。
- **边界条件**：
    - 导入操作为**追加模式**，不覆盖已有记录（ID 冲突时跳过并记录警告）。
    - 题目导入后立即生效（完整性校验通过即可使用，无需内容校对流程，因初始题库已经过人工审核）。**但题目可用性受关联知识点状态约束**：若题目关联的知识点仍处于待校对（`pending_review`）状态，该题目在出题 Agent 的可用题目池中**不可被抽取**，待知识点校对为已启用后自动生效。
    - 所有导入操作记录日志，失败记录单独存储供排查。

## 3. 业务逻辑边界

> 明确哪些事情系统**不做**，避免 AI 过度实现。

- [ ] 不做家长端与教师端，Demo 阶段仅学生端单角色
- [ ] 不做付费订阅、课程售卖、会员体系
- [ ] 不做实时音视频授课、直播答疑
- [ ] 不做完整题库建设，初期仅覆盖 1~2 个科目的三级知识点树；**初始数据通过 JSON 文件批量导入（规则 #10），管理后端提供列表查看与导入操作界面，不提供在线录题界面**
- [ ] **不做知识点全学段全科目覆盖，只保证已启用知识点的粒度适合每日作业**
- [ ] **不做知识点图谱可视化（Demo 阶段仅表格/列表展示掌握度）；先修关系仅存储，不做图遍历诊断**
- [ ] **不做知识点的单条在线编辑（增删改单条知识点内容）；知识点的列表查看、批量导入与校对标记由管理后端提供（§1.1(4)），不属于“在线编辑器”**
- [ ] 不做复杂 RBAC，学生端仅 `openid` 登录态
- [ ] 不做真实支付资金流（本产品无支付环节）
- [ ] 不做消息推送（订阅消息、短信通知；开发者提醒通知除外）
- [ ] 不做多语言、多币种
- [ ] 不做社区、排行、打卡分享等社交功能
- [ ] 不直接让 LLM 输出掌握度数值或整份新计划，必须经结构化校验与后端公式更新
- [ ] **不允许 LLM 自由生成知识点名称或 ID，Agent 只能从已启用知识点列表中选择**
- [ ] 不做试卷手写体高精度 OCR 的兜底人工录入界面（识别失败允许重试，未识别题目由开发者通过后端接口人工归因）

## 4. 维护规则

1. 需求变更时，必须同步更新本文件
2. OpenSpec propose 阶段应参考本文件确认需求边界
3. 发现新的业务规则时，及时补充到本文件
4. Agent 相关规则（规则 #6）变更时，需同步更新 Prompt 版本与 JSON Schema 定义
5. **知识点数据集更新或扩充科目时，必须同步更新规则 #8 中的数据来源与覆盖范围说明**
6. **新增知识点必须走"导入 → 待校对 → 校对 → 启用"流程，不得跳过校对直接启用**
7. **掌握度更新公式（规则 #2）的参数调整需记录变更日志，存放于 `docs/changelog/mastery-formula.md`，并同步更新规则 #2 正文中的公式与参数说明**
